THE RECOMMENDATION

Use speculative parallel — if un-redacted text may reach the summarizer

Conversation PII and conversation summarization take almost exactly the same time on this resource (~2.27 s each). That single fact decides the architecture: the speculative summary runs entirely inside the shadow of the PII call, so it costs nothing in latency. Parallel therefore wins on every clean transcript and merely ties on dirty ones. It is not a latency-versus-cost trade any more — latency favours parallel at every prevalence, and the only question left is whether the extra summarization is worth its money.

If PII may transit the summarizer inside your tenant

Choose speculative parallel. Up to 2.3 s faster per transcript, never slower, and you pay for a second summarization only on transcripts that contain PII.

If the summarizer must never receive PII

Stay sequential. The guarantee is worth roughly 2.3 s per clean transcript — a real cost, but the only design that keeps un-redacted text away from the summarization endpoint entirely.

This is the open question from the customer thread. Speculative parallel sends the raw transcript to the summarization endpoint on every request; the unsafe summary is discarded server-side and never returned, but the text does reach Azure. Everything stays inside the Azure boundary — whether that satisfies the PCI scope is the decision to confirm before adopting parallel.

EVIDENCE · REDACTION QUALITY

Does it catch what it needs to?

Ten hand-labelled transcripts, 41 labelled spans, scored on whether a labelled value survived verbatim in the redacted output — the actual requirement, not span overlap.

GA · default categories98% recall · 1 leak
Preview · explicit categories100% recall · 0 leaks
Spoken-digit card numbersDetected
  • Dates of birth are not redacted on the GA API. DateOfBirth is preview-only and is rejected outright as a category value on 2024-11-01. An identity-verification call that reads a date of birth aloud leaks it. Opting into 2025-11-15-preview fixes it at confidence 1.0, at the price of accepting Microsoft's preview terms.
  • Spoken digits are handled. "four one one one, one one one one…" is caught as CreditCard, as are spoken expiry dates. A speech pipeline without inverse text normalisation does not defeat detection — the main worry going in, and it did not materialise.
  • Last-four references are over-redacted. "the card ending in 4242" is masked despite PCI DSS permitting it. This compounds: the parallel pipeline discards on any detection, so a permitted last-four reference alone makes a transcript count as dirty, inflating effective p and cost.
  • Short turns near card numbers get swallowed. Agent backchannels like "Got it." and "Mhm." were labelled CreditCard at 0.74–0.86 confidence and fully masked. Nothing leaked, but six of nine turns disappeared, leaving the summarizer far less to work with. A confidence floor on short turns would recover most of it.
  • Never send isolated utterances. One turn with no surrounding context redacts badly — a surname survives and a card number is only partially masked, which looks redacted but is not. Send whole conversations.

WHAT WOULD CHANGE THIS

Honest limits

  • Both fixtures are ~600 characters. Real transcripts are far longer, and summarization time grows with input while the PII call may not — if the two stop being equal, the speculative summary stops being free and this recommendation weakens. Re-run this on production-length transcripts before committing.
  • Ten synthetic transcripts is enough to find categorical gaps like the date-of-birth one. It is not enough to estimate a leak rate, and it says nothing about how common each pattern is in real traffic.
  • All measurements come from one Standard-tier resource in eastus2 under no competing load. Latency under production concurrency, and across the three regions in use, is unmeasured.
  • The prevalence sweep assumes transcripts resembling the ones measured. p is not independent of length: longer transcripts are likelier to contain an entity.
